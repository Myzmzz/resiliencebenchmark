# 错误处理是最后一道防线（OSDI 2014）

- 全称：*Simple Testing Can Prevent Most Critical Failures: An Analysis of Production Failures in Distributed Data-Intensive Systems*
- 作者：Yuan 等
- 缓存：`manifestations-v1/docs-cache/STU-SIMPLETEST-OSDI14.txt`（你已缓存但**本轮尚未引用**，`cited_by` 为空）

## 一、它做了什么

Cassandra、HBase、HDFS、Hadoop MapReduce、Redis 五个系统，从问题库里随机抽 **198 起用户报告的生产故障**（只取 Blocker/Critical/Major、2010 年以后、报告人与处理人不同的），逐个追"一个或多个错误如何演变成用户可见的失效"。其中 **48 起是灾难性失效**（全部或多数用户无法正常访问）。然后据此实现静态检查器 Aspirator。

## 二、对你最有用的：故障复现的可行性边界

这几条决定了"一个韧性 benchmark 的实验规模该多大"：

| 发现 | 数字 | 对你的意义 |
|---|---|---|
| 需要几个输入事件才能触发 | 77% 需要多于 1 个，90% 不超过 3 个 | 单一扰动注入覆盖不了大半；但组合深度不用超过 3 |
| **事件顺序重要吗** | 在需要多事件的故障里，**88% 顺序重要** | 你的 episode 编排必须显式声明顺序，"同时注入 A 和 B"和"先 A 后 B"是两个不同实验 |
| 需要几个节点 | **98% 不超过 3 个节点**，84% 不超过 2 个 | 不需要大集群来暴露缺陷。你的三节点环境在这个意义上是够的 |
| 是否确定性 | **74% 确定性**——给对事件序列就一定复现 | 大部分条目应该能写成可重复的实验；剩下 26% 里有 53% 只在输入事件上有时序约束 |
| 能否用单元测试复现 | **77% 能** | |
| 只在长跑系统里出现 | 38% | 这部分是短实验窗口看不到的，需要显式的"长跑"episode |

第三条要注意论文自己的补充说明：这**不等于**"大集群不更容易出问题"。大集群工作负载更杂、故障模式更多，出问题的概率更高；这条说的是**一旦给定了那个特定的事件序列，小集群就足以复现**。

## 三、对你最有用的：92% 的灾难性失效来自错误处理

这是全篇的核心结论链：

1. **几乎所有（92%）灾难性失效，都是对"软件里已经显式发出信号的非致命错误"处理不当造成的**。也就是说，底层错误本身不致命，是处理它的代码把事情搞砸的。
2. 对照组很有说服力：非灾难性失效里只有 **25%** 涉及错误处理不当。所以在多数情况下错误处理是有效的，**恰恰是它失效的那些场合，后果最严重**。
3. 开发者其实很会预判错误——198 起里只有一起是错误返回值压根没检查（Redis）。问题不在"没catch"，在"catch 了以后处理得潦草"。

**35% 的灾难性失效栽在三种平凡模式上**（不需要懂系统就能看出来）：

- *忽略显式错误*（25%）：catch 块是空的，或只有一行 log。论文的 HBase 例子是数据丢失，补丁就是在 catch 块里加重试。
- *过宽捕获后终止集群*（8%）：`exit()` 本来只想给 `IncorrectVersionException` 用，但代码 catch 的是 `Throwable`；namenode 一次抖动让 `registerDatanode()` 抛了 `RemoteException`，被 `Throwable` 兜住，**所有 datanode 一起退出**。
- *catch 块里写着 TODO/FIXME*（2%）。

另外 **23%** 是系统相关但同样易测的：**只要错误处理那个基本块被执行到，失效就 100% 暴露**——纯粹是从来没被测过。剩下 34% 是真正复杂的。

## 四、对你最有用的：自下而上的测试策略

这一节直接冲着"随机故障注入"去：

> 现有的错误处理测试大多是**自上而下**——用测试输入启动系统，在各个阶段主动注错。论文的建议是**自下而上**：从已有的错误处理代码块出发，反推出一个能到达它的测试用例。

理由是：这些残留的生产故障需要**罕见的事件序列先把系统带到罕见状态**，然后注入的错误才会打垮服务；加上 38% 只在长跑系统里出现，自上而下要探索的输入空间根本不可控。论文的建议是把符号执行这类技术改造成"定向构造一条到达错误处理块的路径"，而不是从入口盲目探索。

**这条对 ORCAS 那条路线（架构感知地生成实验）是个重要补充也是个警告**：即使你按机制和反模式来选实验，仍然会漏掉那些"需要先把系统带到特定状态"的缺陷。你的 episode 设计里"前置状态"这一段和"注入什么"同样重要。

## 五、Aspirator 的三条规则（可以照抄成 rules-v1 的静态判据）

1. catch 块为空，或只有一条打日志的语句 → 告警；
2. 高层异常（`Exception`/`Throwable`）的 catch 块里调用了 `abort`/`System.exit()`，而这个 catch 块实际会兜住多个不同的低层异常 → 告警；
3. catch 块对应的源码里有 `TODO`/`FIXME` → 告警。

**降误报的两条启发式**（这部分同样值得抄）：
- try 块里改了变量 V，且 catch 块之后紧跟的基本块检查了 V → 不告警（错误在 catch 块外面处理）；
- try 块最后一条是 `return`/`break`/`continue`，且 catch 块之后的块非空 → 不告警。
- 运行期可配置：允许忽略指定异常（论文忽略了全部 `FileNotFound`），允许排除 `shutdown`/`close`/`cleanup` 方法里的告警（系统反正要停了）。

结果：9 个系统里报出 121 个新缺陷 + 379 处不良实践，143 个被开发者确认或修复——**而这些系统已经在用 FindBugs 和自建的错误注入框架了**。
