# Operator 自身的可靠性（NSDI 2026）

- 全称：*Who Watches the Watchers? On the Reliability of Softwarizing Cloud Application Management*
- 作者：Gu、Tang、Su、Stoica、Sun、Zheng（UIUC）、Zhang、Rahman（Auburn）、Wang（IBM Research）、Xu（UIUC）
- 缓存：`docs-cache/LIT-OPERATOR-GU26.txt`
- 制品：https://github.com/xlab-uiuc/acto/tree/nsdi26-ae

## 一、它做了什么

13 个成熟的 Kubernetes Operator（K8ssandra/Cassandra、EDB 与 Zalando 两个 PostgreSQL operator、CockroachDB、Strimzi/Kafka、Knative、KubeBlocks、MinIO、Percona/MongoDB、RabbitMQ、Solr、TiDB、Pravega/ZooKeeper），每个随机抽 100 个已关闭且已修复、根因清楚的问题单，最终留下 **412 起 operator 失效**，每起至少两人独立分析。然后做了测试工具 OAT，在 6 个 operator 的最新版上找到 **86 个新缺陷**（53 个已确认、28 个已修复），**零误报**。

这是列表里唯一一篇把研究对象放在"负责自动管理和恢复的控制器"上的论文，也是最新的一篇。

## 二、最该搬走的：交互维度的根因分类

它把 operator 的复杂度拆成四类**交互**，而不是拆成代码模块：

| 交互对象 | 失效数 | 占比 | 说的是什么 |
|---|---|---|---|
| ① 被管应用 | 91 | **42%** | 调应用 API、改应用配置、准备执行环境、给应用申请资源 |
| ② 云平台（K8s） | 65 | 30% | 通过创建/更新 API 对象来管 pod、卷、网络 |
| ③ 同处一地的其他控制器 | 9 | 5% | 两个控制器管同一批资源（如 Istio 注入 sidecar 改了网络策略） |
| ④ 用户接口（CR/CRD） | 50 | 23% | 声明式接口实现得对不对 |

**Finding 1**：52.2% 的 operator 失效源于与外部实体的交互缺陷，是 operator 内部程序缺陷（25.2%，空指针、逻辑错等）的两倍。

**Finding 2**：交互类失效里 **62.3% 后果是灾难性的**——被管应用全站不可用 50.2%、部分不可用 8.8%、静默丢数据 3.3%；另有 29.3% 是"应用行为不对但没明显中断"（配置错、性能退化、副本数不对、权限不对），**这类更难发现**。只有 8.4% 的后果落在 operator 程序自己身上（崩溃、挂起）——作者认为这反而是最轻的，因为没有直接影响生产应用。

> **这四类交互可以原样变成你目录的一个新机制组**。理由：你现在的 11 个机制组全是"应用侧或平台侧的防护动作"，没有一个覆盖"谁在执行恢复动作"。而 K8s 环境里，副本数、滚动更新、故障转移、扩缩容这些**恢复动作的执行者就是控制器**。控制器判断错了状态、顺序搞反了、或者在应用还没准备好的时候就动手，表现出来和"副本数配错"完全不同。

## 三、失效模式（Table 4 / Table 5）——每一条都能对上你的 a–g

91 起"管应用失败"的四种模式：

| 模式 | 占比 | 你的类别 |
|---|---|---|
| **违反应用的操作语义** | 63.7% | b（不该动乱动）为主 |
| **看不见应用内部状态** | 16.5% | a（该动不动）/ 观察盲区 |
| **版本不兼容** | 12.1% | a/b 均有 |
| **误处理应用返回的错误** | 7.7% | a |

"违反操作语义" 58 起再细分（Table 5）：

- **配置（36.2%）**：**14 起配置类失效，14 起全部是跨参数、跨组件或跨节点的深层语义**——论文明说"我们没有观察到任何传统的配置错误（没有单个参数写错的）"，猜测是自动化本身消灭了手误。11 起涉及跨节点/跨组件的相互依赖。另有 7 起是"operator 以为改成功了，应用其实还在用旧配置"——因为应用的配置接口太复杂（多个文件有覆盖关系、多个数据库作用域不同），改错了地方。
- **顺序（31.0%）**：12 起根本没强制顺序（异步操作里先发的不保证先完成），6 起顺序强制错了。有个漂亮的死锁例子：KubeBlocks 随机顺序启动 PostgreSQL 节点，某次先启了 follower，follower 等 leader 加入 quorum，而 KubeBlocks 又在等 follower 就绪才启 leader——**互等**。
- **前置条件（19.0%）**：单个操作的前置条件。PostgreSQL failover 至少有三个前置条件（目标节点就绪、WAL 不滞后、在同步复制模式下角色是 SyncStandby），同一个 operator 修了三次、每次才发现一个。**Finding 8：前置条件违反主要发生在"处理故障"（failover）和"缩容"这两类操作上**——它们的前置条件最微妙、影响最大。还有一例：CN/PostgresOp 在磁盘满时做 failover，没检查目标节点磁盘余量，而目标节点容量相同也满了，**failover 让问题更严重而不是解决它**。
- **执行环境（13.8%）**：目录/文件没建或权限不对。**这 8 起全部发生在"改造已有环境"或"从备份恢复环境"时，没有一起发生在干净启动**。

## 四、探针相关的证据（直接补你 gaps.md 的空缺）

§4.2 State Observability 的 15 起里，**8 起是探针不可靠**：

- **就绪探针用近似信号**：用容器启动、DNS 解析能否成功来代表应用就绪，这些信号是不稳的。MongoOp-1334 用 **TCP 连接成功**作为 MongoDB 的就绪探针，滚动升级时 MongoDB 能建 TCP 连接但还在 booting 阶段——`a` 类（该摘没摘 / 不该放进来却放了）。
- **存活探针误杀**：3 起（[21][30][47]）全部是**应用运行变慢时探针自己超时**导致误报，把健康实例重启。修法是加大超时、降低探测开销，作者直说这是绕开而不是根治。
- **探针只对特定配置有效**：MariaDBOp-1096 用 prepared statement 作存活探针，当 MariaDB 配了 `max_prepared_stmt_count=1` 时这条语句失败，**持续重启健康的 MariaDB 实例**——这是 `probe b` 的极好案例，而且它说明探针的有效性依赖被测应用的配置。

论文对探针的总体评价值得引用：他们检查了这些 operator 实现的探针，**大多数用的是简单、脆弱的检查（例如发一个假的客户端请求），无法应对真实的失效模式（慢失效、灰色失效、部分失效、亚稳态）**，尽管已经迭代过很多轮。

另外 7 起是**状态编码问题**：operator 没法判断"当前状态"和"期望状态"语义上是否相等，于是**明明已经达到期望状态还在不停调谐**。KafkaOp 的例子：期望配置 `timeout.ms=1000`，从 Kafka 读回来的是字符串 `"1000"`，`"1000" != 1000` → 写配置、重启 Kafka、每两分钟一轮，**无限重启**。这是 `c` 类（无界）在控制器上的形态。CN/PostgresOp 用 `pg_ctl status` 的文本输出判断实例是否停止，换个 locale 输出就变了。

## 五、误处理应用错误（7 起，但两种方向相反的形态）

- 5 起是**没处理**：应用返回错误，operator 直接退出。CassOp 的 decommission 失败（Cassandra 节点磁盘满），**用户把磁盘扩容解决了问题以后，operator 再也没重试过**——缩容永久卡住。这是 `retry a`（该重试不重试）在控制器层的形态。
- 2 起是**处理错了方向**：TiDBOp 把 pod 里的所有错误都当成瞬时错误，等它自己恢复再做别的操作。但永久性错误会让 operator 一直挂着，**挡住了本可以缓解故障的扩容操作**。修法是让扩容的优先级高于等待 pod 恢复。

第二条特别值得记：**"无限等待瞬时错误恢复"会阻塞恢复动作本身**，这是 e 类（不恢复）的一个干净机理，而且完全是机制内部造成的，与外部负载无关。

## 六、最该搬走的：OAT 的测试策略表（Table 6）

这张表就是**"机制缺陷形态 → 用什么操作和什么故障去逼出它"**的映射，和你正在建的东西是一回事：

| 失效模式 | 操作命令（改期望状态） | 注入的故障 |
|---|---|---|
| 语义-配置 | 改应用配置 | 无 |
| 语义-顺序 | 改应用特有属性 | **延迟操作**（阻塞 operator 的网络请求直到观察到后续请求，强制换一个顺序） |
| 语义-前置条件 | 改应用特有属性 | **杀应用容器** |
| 语义-执行环境 | 改应用的 security context | 无 |
| 状态可观测性 | 改应用特有属性 | 无 |
| 错误处理 | 改应用特有属性 | **操作超时**（网络分区） |
| 版本不兼容 | 改应用镜像版本 | 无 |

注意三件事：

1. **只注入瞬时故障**（节点崩溃、网络延迟、连接超时），因为这些是真实部署里常见、且 operator 本来就应该处理的。故障用 **Chaos Mesh** 打。
2. **"持久故障 + 撤除 + 检查最终收敛"**：为了测容错，OAT 先注入一个**持久**故障让调谐无法完成，再声明一个新的期望状态触发调谐，然后**把故障撤掉，检查应用状态最终是否匹配新的期望状态**。这就是你 taxonomy.md 里 e 类"判据只能取在故障撤除之后"的一个可执行协议——而且它比单纯"撤除后观察"更强，因为它保证了故障期间确实有未完成的工作。
3. **正常操作不应该影响可用性**是一条独立的判据：OAT 要求普通操作命令期间应用可用性不下降，注入瞬时故障时可用性不低于 **95%**。

## 七、最该搬走的：判据（oracle）必须超出平台 API

**Finding 16：86 个缺陷里 43%（37 个）必须靠应用特有的状态监视器和工作负载才能抓到。** 这些缺陷用"检查崩溃、错误日志、K8s 状态对象"这种常规判据是看不见的——33 个表现为**应用真实配置状态与 ConfigMap 对象不一致**，4 个表现为**状态转换期间的瞬时不可用**。

对应两种用户自备的工具：

- **状态监视器**：以 MariaDB 为例，跑 `SHOW VARIABLES` 拿当前配置 → 解析成键值对 → 与声明的期望配置比较。作者说配置状态监视器"实现起来很容易，但对检测配置类语义违反非常有效"。
- **应用工作负载**：周期性读写请求，**在状态转换的整个过程中**持续测成功率。因为"操作完成后再检查状态"看不见过程中的可用性违反——比如滚动升级时破坏了多数派 quorum。

> **这一条直接对上你 gaps.md 的 3.1 节**。你写"f/g 类空缺是因为组件文档只描述机制行为不描述业务后果，要写条目就得自造业务场景"，并建议"这些格子不应靠文献补齐，而应在具体被测系统上通过业务断言实验产出"。Gu 这篇给了这条建议一个可引用的方法论依据和一套具体做法：**判据分两层——平台可见的状态对象一层，应用内部状态 + 过程中可用性一层**，后者要为每个被测应用写 88–208 行 Python。这个量级是可接受的。

## 八、成本数据（对你规划实验预算有用）

6 个 operator，每个生成 339–2480 个测试、注入 24–259 次故障、耗 **6.2–63.2 机时**；接一个新 operator 大约 **8 人时**。属性取值 82.2% 能从项目里已有的单元测试和示例中挖出来，其余用 GPT-4o 合成（**78% 有效**），每个 operator 平均 11761 token，约 0.005 美元。

## 九、论文自己承认的局限与几条反向提醒

- OAT 的探索策略**不保证完备**。
- **Finding 15：86 个缺陷里 62.8% 的代码级形态不在他们自己的研究分类里**。作者由此得出结论：**只针对已知缺陷模式去找是不够的**。这对你是个直接的方法论提醒——你的规则库和表现目录是基于已知模式建的，它能覆盖的那部分之外还有大头。真正起作用的是"系统地激发交互 + 强判据"，而不是"枚举模式"。
- **Finding 14：应用管理的官方文档太含糊，且缺失重要的操作语义**。46 个语义违反里 **13 个根本没有文档描述**（比如改 Cassandra 已有集群的 `num_tokens` 的要求，只存在于博客和经验报告里）。其余 33 个有文档但含糊（MariaDB 文档说重启节点前要"把所有客户端连接转移到其他节点"，但没说具体怎么做；真正的前置条件是先做 primary stepdown）或**散落在文档各处**（MariaDB 恢复操作的一个前置条件写在"已知问题"一节里）。
  > 这条对你 rules-v1 的"从官方文档建规则"路线是个重要的边界说明：**官方文档不足以定义正确的管理操作语义**，规则库里凡是涉及"操作的前置条件"的部分，文档来源的置信度应该打折。
