# 软熔断：用缓存做熔断的执行器（arXiv 2021）

- 全称：*Towards Soft Circuit Breaking in Service Meshes via Application-agnostic Caching*
- 作者：Larsson、Tärneberg、Klein、Kihl、Elmroth（于默奥大学 / 隆德大学）
- 缓存：`docs-cache/LIT-SOFTCB-ARXIV21.txt`
- 状态：2021 年 arXiv 预印本，非会议正式发表。规模小、结论偏工程可行性验证。

## 一、最该搬走的：把熔断拆成三段

论文开篇给了一个一句话的分解，这是全篇对你最有价值的东西：

> 熔断由三部分构成：**观察相关指标的传感器（sensor）**、**把观察到的指标转换成过载信号的决策机制（decision）**、**针对过载采取行动的执行器（actuator）**。

然后指出：**当前服务网格里的执行器全是"开/关"型的**——熔断跳闸就返回一个表示服务不可用的应用级错误。论文换掉的只是第三段。

这个三段分解的价值在于**它不止适用于熔断**。把它套到你的每个机制组上，机制内部的缺陷位置立刻变得可定位：

| 机制 | 传感器（看什么） | 决策（何时算触发） | 执行器（触发后做什么） |
|---|---|---|---|
| 超时 | 已等待时长 | 超过阈值 | 中断等待并返错 |
| 熔断 | 失败率／并发额度 | 超过阈值且样本足够 | 快速失败／**返回缓存** |
| 探针 | 探测响应 | 连续 N 次失败 | 摘除／重启 |
| 过载保护 | 排队时延／CPU／并发 | 超过目标 | 丢弃／排队／发额度 |
| 取消 | 上游放弃信号 | 收到即算 | 停止执行并清理 |

**同一个 a 类（该动不动）可以出在三个不同位置**：传感器看不到（Gray Failure 说的观察盲区）、决策阈值算错（样本不足、窗口不对）、执行器没执行（熔断打开但流量仍在走）。你目前 a/b 的判据说明只区分了"机制动了没动"，加上这一层可以让 `distinguishing_signals` 写得更准——**先证明信号到没到传感器，再证明决策有没有翻转，最后才看执行**。

## 二、可用的量化结论

- 用两种自适应 TTL 估计算法（从 Web 内容缓存领域搬过来的），在自建的 value service 上，**数据陈旧率保持在约 3% 或以下时，网络负载降低最多 30%**。
- 在 Google Cloud 的 Hipster Shop 微服务基准上，**约 80% 的服务间请求能用缓存应答，整体网络流量降低 40%**。
- **一个客户端请求平均分叉成约 13 个服务间请求**。

## 三、一个对"缓存降级"很关键的结构性观察

论文论证"为什么只在面向客户端的边缘缓存不够"时给了一个直接可用的判据：

> 聚合结果的 TTL 受其构成子结果中**最小的那个 TTL** 约束。

推论：13 个子请求里只要有一个 TTL 很短，聚合响应就会失效，**所有请求都得重新发一遍**。这解释了为什么只在入口做缓存收益很低，也给了你一个可写成公式的量：`TTL_聚合 = min(TTL_子请求 i)`。

这条还能反过来用在你的目录上：**fallback 组的"降级返回缓存"条目，其陈旧程度不是由本层 TTL 决定的，而是由整条调用链上最短的那个 TTL 决定的**。判定"返回的是不是过期数据"时要沿链看，不能只看返回那一跳。

## 四、为什么服务间不做缓存（非技术原因才是主因）

论文认为技术障碍都是可工程化解决的（gRPC 所有操作都用 POST，通常不被认为可缓存；协议版本不对等等）。真正的障碍是：

- **开发期无法先验确定 TTL**——除非底层数据本身已知稳定（比如每小时更新的天气预报）。论文的解法是运行期检查响应内容、动态估计 TTL。
- **判断哪些操作可缓存本身是个问题**。REST 靠 HTTP 动词映射来强制区分是否改变状态，gRPC 在协议层没有这种强制。

服务间缓存与 Web 内容缓存的三点实质差异（决定了算法选型）：更新更频繁所以 TTL 更短；对象流行度方差大（不由人的偏好决定）；计算和响应必须快，否则会被扇出倍数放大。

## 五、对你目录的具体用法与边界

- 可以支撑 `fallback` 组的条目：缓存降级的收益-陈旧权衡有了量化数字（3% / 30%、80% / 40%）。
- 注意它**只是可行性验证**：两个算法、两个基准、预印本。不要把 80%/40% 当成普适数字，写进条目时要写清实验环境。
- 缓存降级是否适用高度依赖业务对数据新鲜度的要求——这正是你 `requires_business_assertion` 标记存在的理由。一个"熔断后返回缓存"的系统在标准遥测上看起来完全健康（成功率 100%、延迟更低），只有业务断言能发现返回的是旧值。**这类条目必然落在 g 类且必然需要业务断言。**
