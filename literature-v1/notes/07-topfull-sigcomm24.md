## 一、最该搬走的：局部保护导致的"饥饿"

这是全篇对你最有价值的东西，而且是一个**你目录里现在没有的缺陷形态**。

场景（论文 Figure 1）：两个微服务 M_A（容量 10k rps）和 M_B（容量 3k rps），两个 API 各以 10k rps 到达。API1 的调用路径是 M_A → M_B，API2 只经过 M_A。

- **理想分配**：API1 拿 3k、API2 拿 7k，总 goodput 10k。
- **现有的按微服务限流**（DAGOR、Breakwater 这类）：M_A 上 API1 和 API2 被**同等**限到 5k；M_B 再把 API1 限到 3k。结果 API1 实际吞吐 3k，总 goodput 只有理想值的 80%。
- **浪费在哪**：M_A 上有 2k rps 的 API1 流量**被处理了，但因为下游拒绝，响应是残缺的、最终被丢弃**。这部分资源本可以给 API2。

论文的措辞很准确：**"起初在 M_A 被处理、但最终因为响应不完整而被丢弃"**。这种"上游做了功但被下游作废"的浪费，在标准遥测里非常难看出来——M_A 的成功率看起来正常（它确实处理完了），M_B 的拒绝率也正常（它在正确地限流），**只有端到端 goodput 是低的，而且没有任何单个组件为此负责**。

### 为什么这对你重要

1. **这是一个纯 `interaction` 类的表现**：去掉任何一个限流器都不会出现。你的 `interaction` 组目前 6 条集中在 b、d、e，这条属于 d（局部故障沿依赖扩散 / 请求量被放大）——而且它的放大链是**反向**的：下游的保护动作把上游的资源变成了浪费。
2. **它有可量化的下限**。饥饿发生的条件是：某个 API 在其执行路径上有**多于一个**过载的微服务，且在其中某个过载微服务上还有别的 API 与它竞争。
3. **它很常见**，论文给了两组数据：
   - Online Boutique 上分别给 5 个 API（postcheckout、getproduct、getcart、postcart、emptycart）单独打流量，**任何一个 API 的流量突增都会造成多个微服务过载**，平均 3.4 个——即饥饿的前提条件总是满足。
   - 分析阿里巴巴 trace 的 **23481 个微服务**（CPU 利用率 > 0.8 算过载），**在涉及过载微服务的 API 中，44.4% 潜在地容易发生饥饿**。
   - 实测：DAGOR 下 Get Product 被饿死，比 API 级限流少服务 **65.5%** 的请求；TopFull 在 Post Checkout 服务量相同的前提下多服务 **1.9 倍** Get Product。

## 二、方法上可借鉴的三点

1. **在入口按 API 限流，而不是在每个微服务限流**。要做到这点需要**分布式追踪提供 API 的执行路径**，以及每秒采集一次微服务资源利用率。
2. **降速和升速要用不同的判据**（这是避免饥饿的关键，不是 RL 的功劳）：
   - 降速时：把使用目标微服务的 API **同等降速**以解除过载；
   - 升速时：**先检查该 API 的执行路径上此刻还有没有别的过载微服务，只升那些路径上已经没有过载的 API**。
   - 选择目标微服务的顺序也有讲究：**优先选被最少 API 使用的那个过载微服务**，因为它最不容易被后续针对其他微服务的限流所影响。
3. **聚类实现并行控制**：把共享过载微服务的 API 聚成一簇（传递闭包：即使 API1 和 API3 不直接共享，只要存在 API2 与两者都共享，三者同簇）。簇之间互不影响，可以并行控制。过载集合变化时动态重新聚类。**分叉执行路径的 API 按"涉及其所有可能路径上的全部微服务"处理。**

RL 控制器（决定倍率步长，观察 goodput 和端到端分位延迟，Sim2real 训练）是实现手段，对你参考价值不大。

## 三、可引用的效果数字

- goodput：比 DAGOR 高 **1.82 倍**，比 Breakwater 高 **2.26 倍**。
- 与 K8s autoscaler 配合：流量突增时多服务 **3.91 倍**请求；承受同样的流量尖峰**少用 50–57% 的资源**。
- 论文明确指出 autoscaler 的根本局限：**扩容要几秒到几分钟**，这期间 goodput 会出现短暂但严重的退化。

> 最后这条对你的 `replica-pdb` 和 `overload` 两组之间的交互很有用：**扩缩容不是过载保护的替代品，它的时间常数差了两三个数量级**。一个"配了 HPA 所以不需要限流"的系统，在流量突增下的表现应该是可预期地差——这可以写成一条 `interaction` 条目，强度下限就是 HPA 的 `stabilizationWindowSeconds` + 镜像拉取与启动时间。

## 四、边界

- 论文对"过载"的判定用的是 **CPU 利用率 > 0.8** 这个阈值。结合 Breakwater 对 CPU 信号的批评（磁盘瓶颈时 CPU 很低），这个判据在非 CPU 瓶颈的场景下会失效。两篇放在一起读，正好说明**过载信号的选择本身就是一个缺陷来源**。
- 需要完整的分布式追踪覆盖。没有 trace 就没有执行路径，整套方法不成立——这也是对你 benchmark 的一个环境要求。
