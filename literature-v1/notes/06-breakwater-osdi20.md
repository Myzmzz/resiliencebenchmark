# Breakwater：微秒级 RPC 的过载控制（OSDI 2020）

- 全称：*Overload Control for μs-scale RPCs with Breakwater*
- 作者：Cho、Saeed、Fried、Park、Alizadeh、Belay（MIT CSAIL）
- 缓存：`docs-cache/LIT-BREAKWATER-OSDI20.txt`

## 一、它解决的问题

服务时间在微秒量级的 RPC（内存型 KV、内存数据库），**丢一个请求的代价和处理一个请求的代价差不多**。这让两类传统过载控制都失效：

- **服务端丢弃（AQM 类）**：丢弃前仍要处理和解析包，还要生成失败消息（RPC 服务端通常被要求成功失败都回应，以免客户端走昂贵的超时）。请求越短、客户端越多，这部分开销占比越大。论文实测 CoDel：随客户端需求上升，越来越多 CPU 花在包处理上，**尽管绝大多数请求最后被丢掉**，goodput 反而下降。
- **客户端限速**：客户端要先知道服务端的拥塞状态，这至少要一个 RTT。当 RPC 执行时间和 RTT 相当时，反应延迟严重伤性能。而且**客户端越多，每个客户端的请求越稀疏，它对服务端状态的估计越陈旧**——要么欠发要么过发，过发就形成 incast。基于窗口的限速还有个结构性问题：窗口最小也是 1，**每个客户端总能发一个请求**，客户端一多就把服务端压垮。

## 二、最该搬走的：过载信号该选什么

论文逐个否掉了常见信号，理由都能直接用：

| 候选信号 | 为什么不够 |
|---|---|
| **CPU 利用率** | 只反映一种资源竞争。请求争抢磁盘时延迟很高但 CPU 很低；而且**无法区分"100% 利用率且无请求超时"这个理想状态和 livelock 状态** |
| **队列长度** | RPC 服务时间离散度大时，队列长度不能很好地指示请求延迟 |
| **排队时延** | 服务时间有变化时依然准确，而且**从目标 SLO 映射到目标排队时延是直观的** ← 选它 |

这张表对你的 `overload` 机制组是直接可用的判据素材：你要判"过载保护该动没动"，得先确认它盯的是哪个信号；**盯 CPU 的保护机制在磁盘瓶颈下必然是 a 类（该动不动），这不是配错阈值，是选错信号**。

**还有一条关于测量本身的精细要求**：排队时延必须**把请求经历的每一段排队时延加总，同时排除非过载引起的延迟**。Breakwater 有两段排队（包等待处理、线程等待执行），两段都打时间戳、都计入。而且他们发现最大的"假延迟"来源是线程模型——最初用的 in-line 模型（一个线程同时做包处理和请求处理）CPU 开销最低，但**一个长请求会阻塞同核上的其他请求造成队头阻塞，那不是资源不足，是负载均衡差**。所以改用 dispatcher 模型。

> 对你的意义：**"排队时延升高"这个信号本身可能来自队头阻塞而不是过载**。你的目录里 overload 组的条目在写 `distinguishing_signals` 时应该要求区分这两者——否则会把"负载不均"误判成"过载保护该动没动"。

## 三、机制设计（了解即可，不是重点）

服务端驱动的信用（credit）准入控制：客户端只有拿到信用才能发请求。每个 RTT 按排队时延更新总信用 `C_total`：

- `d_m < d_t` → 加性增：`C_total ← C_total + A`
- 否则乘性减、减幅与过载程度成比例：`C_total ← C_total · max(1 − β·(d_m − d_t)/d_t, 0.5)`

其中 `A = max(α · n_c, 1)`（与客户端数成正比，控制超发力度），β 控制对队列堆积的敏感度。配套两个技巧：**需求推测**（客户端只在能搭便车时才捎带需求信息，服务端对其余客户端靠猜，随机发信用）和**超发**（每客户端可超发 `C_oc = max((C_total − C_issued)/n_c, 1)`）。超发会偶尔造成突发，用延迟型 AQM 兜底丢弃。信用搭在响应上、需求搭在请求上，尽量不产生独立消息。

客户端侧一个值得注意的设计：**请求可以在客户端过期**——服务端驱动意味着客户端要等准入，队列太长时端到端延迟就爆了，所以按 SLO 设一个客户端侧过期时间。

## 四、可引用的收敛数字

客户端需求突增到容量的 **1.4 倍**时：
- Breakwater **在 20 ms 内收敛到稳定性能，没有拥塞崩溃**；
- DAGOR 需要 **500 ms** 从拥塞崩溃中恢复；
- SEDA 需要 **1.58 s**。

这三个数字是"保护机制的反应速度"的量级参考。它们也说明：**同样是"有过载保护"，恢复时间能差 80 倍**——你的规则库如果只判"是否配置了限流"，这个差别完全看不见。要判出来，实验必须测"从过载开始到 goodput 恢复的时间"，而不只是"最终有没有恢复"。

## 五、对你目录的用法

- `overload a`（过载保护该动不动）：补上"选错信号"这个根因，附 CPU/队列长度/排队时延的对比。
- `overload d/e`：拥塞崩溃（congestion collapse）与恢复时间是可测量的量。DAGOR 500ms、SEDA 1.58s 这两个数说明保护机制存在但**收敛慢**本身就是一种缺陷形态——它不属于 a（机制确实动了），也不属于 b，接近"机制生效但时间常数不合适"。这在你现有的 a–g 里没有直接对应的格子，最接近 d（时长被放大）。值得在 taxonomy.md 里想一下要不要作为 a 的一个子形态写进判据说明。
- 边界：这是微秒级 RPC 的设定，你的被测系统（Spring Cloud / Dubbo 类微服务）服务时间在毫秒到百毫秒量级，"丢弃代价≈处理代价"这个前提不成立，所以**结论不能直接搬**，能搬的是信号选择的论证和测量方法。
