# WASABI：重试缺陷（SOSP 2024）

- 全称：*If At First You Don't Succeed, Try, Try, Again...? Insights and LLM-informed Tooling for Detecting Retry Bugs in Software Systems*
- 作者：Stoica、Sethi、Su、Zhou、Lu、Mace、Musuvathi、Nath（芝加哥大学 + 微软研究院）
- 缓存：`manifestations-v1/docs-cache/STU-RETRY-STOICA24.txt`（本目录已引用为 `STU-RETRY-STOICA24`）

## 一、它做了什么

两件事。第一件是实证研究：从 8 个 Java 开源系统（Elasticsearch、Hadoop Common/HDFS/Yarn、HBase、Hive、Kafka、Spark）的问题库里，按 `retry`/`resubmit`/`reattempt`/`reschedule` 四个关键词捞出 70 个 2018-04 到 2023-11 之间已修复的重试缺陷，逐个读描述、评论、补丁和相关源码。第二件是工具 WASABI：静态分析 + 大模型 + 故障注入 + 复用已有单元测试，在 8 个系统上报了 191 条，人工确认 109 条为真缺陷。

## 二、最该搬走的：三问式缺陷分类

论文把重试缺陷按**机制的三个决策点**分类，而不是按症状或组件分类。这是全篇最值钱的结构：

| 大类 | 子类 | 条数 | 说的是什么 |
|---|---|---|---|
| **IF 该不该重试**（36%） | 重试策略错 | 17 | 可恢复错误没重试（8）／不可恢复错误被重试（9） |
| | 机制缺失或被关掉 | 8 | 本来有重试的机会，代码里压根没写 |
| **WHEN 何时重试**（33%） | 无退避 | 10 | 两次尝试之间没有任何 sleep |
| | 无上限 | 13 | 次数／时长没有封顶，或封顶算错 |
| **HOW 怎么重试**（31%） | 状态没重置干净 | 12 | 上一次留下的半成品让后续每次都失败 |
| | 任务追踪被破坏／竞争 | 8 | 原任务与重试任务共用 key，元数据被写坏 |
| | 其他 | 2 | |

**IF 类的四种具体形态**（都有可引用的案例）：

1. *错误码清单漏项*。Kafka 有 74 个应用级错误码，消息处理和响应处理在不同的类里，开发者漏掉了 `UNKNOWN_TOPIC_OR_PARTITION`——这个错误在 broker 初始化期间提交消息时出现，初始化完成后重试就能成功（KAFKA-6829）。
2. *依赖库升级后清单没跟上*。HBase 依赖的 ZooKeeper 库升级后开始返回新的瞬时错误 `KeeperException.RequestTimeout`，HBase 一年多没跟进（HBASE-25743）。同类：KAFKA-12339。
3. *错误粒度太粗，把不可恢复的裹进去了*。Hadoop Common 的重试策略重试 `IOException`，但它的子类 `AccessControlException` 是权限失败，不该重试（HADOOP-16580）。更隐蔽的是错误在传播路径上被包了一层：`setupConnection` 正确地不重试 `AccessControlException`，但别的路径把它包进 `HadoopException`，而后者总是被重试（HADOOP-16683）。
4. *把"取消"当成可恢复错误*。Elasticsearch 的 `ResultsPersisterService` 在任务被取消后仍然无限重试写结果（ES-53687）；Hive 的任务处理器把被取消的 TezTask 当作失败重新入队（HIVE-23894）。

> **这一条直接补上你 gaps.md 里 `retry b`（不该重试却重试）的空缺**——你当时判断"Stoica 的 IF 类给的是统计分类不是可复现表现"，但 §2.2.1 里四个案例都写到了具体代码路径和触发条件，HADOOP-16683 和 HIVE-23894 尤其可以写成条目。

## 三、重试不是"一个循环"

统计上：**55% 的重试是简单循环，45% 不是**——25% 是异步任务重新入队（把请求封成 task/message 再丢回队列），20% 是状态机（失败时不推进状态，由执行器重新驱动同一状态）。

对你的意义有两层：

- **判据层面**：你在 rules-v1 里写"是否配置了重试"这类规则时，只查循环或只查 `maxRetries` 配置项会漏掉将近一半。状态机式重试连"重试了几次"都很难从外部数一遍。
- **表现层面**：状态机重试的"无退避"形态和循环式完全不同。HBASE-20492 里 `UnassignProcedure` 在 `REGION_TRANSITION_DISPATCH` 状态失败后故意不改状态好让执行器重试，因为失败得太快，把 `StateMachineExecutor` 堵死，**别的 procedure 全都推不动**——而且重启无效，因为 procedure 的状态是持久化的。这是"重试无退避"跨任务放大的一个干净例子，属于 d 类，你目前 retry 组的 d 类只有一条。

## 四、最该搬走的：三个与业务无关的测试判据

WASABI 的 oracle 设计值得整段照抄，因为它们**不需要懂被测系统的业务语义**：

| 判据 | 怎么判 | 抓哪类 |
|---|---|---|
| **missing cap** | 同一个注入点被触发 100 次，或单个测试跑超过 15 分钟 | WHEN-无上限 |
| **missing delay** | 在两次连续注入之间，检查日志里有没有从同一个协调方法栈上发出的 sleep 调用（`Thread.sleep`/`Object.wait`/`TimeUnit.sleep`/`Timer.schedule` 等） | WHEN-无退避 |
| **different exception** | 测试最终抛出的异常≠注入的异常 → 可疑 | HOW 类 |

第三条的巧妙之处在于它同时消化了静态分析的误报：如果某处根本不是重试点，注入的异常会原样抛出来，判据自动判为"非缺陷"。

**注入次数决定能看见哪类缺陷**，这条对你的实验设计最直接：

- 注入 **1 次** → 让重试之后的代码真的跑起来 → 暴露 HOW 类（状态没清理）。论文里 HDFS 的例子：注一次 `SocketException`，测试挂在 `NullPointerException` 上——因为瞬时错误发生得太早，对象还没构造完，而 catch 块假设对象都在，打日志时就空指针了。
- 注入 **100～1000 次** → 撑满上限和退避机制 → 暴露 WHEN 类。但这时重试之后的应用代码可能根本不执行（超时了）。

所以**同一个注入点必须跑两轮不同强度**，一轮不能兼顾。你现在 manifestations.yaml 的 `intensity_lower_bound` 写的是"多大故障才触发"，这里补的是另一个维度：**同一强度下，注入持续多久/多少次，决定你看见的是哪一类表现**。

## 五、测试环境本身会掩盖机制

两条很实在的发现：

- 这 8 个系统里只有 **0.1%–0.5%** 的用例被标为与重试相关；大约 10% 的用例会走到可能触发重试的代码，但**测试中几乎从不真的发生重试**，因为瞬时错误太罕见。
- **约 10% 覆盖重试逻辑的用例里，开发者手动把重试上限改成了 0、1 或 2**。WASABI 专门写脚本扫描并把这些值改回配置文件里的默认值。

第二条对你是个警告：**被测系统在测试/演示环境下的机制参数，可能和生产不是一回事**。你的 harness 在部署被测应用时，如果沿用 demo 的 values 文件，测出来的"有没有重试"可能是装置的结论而不是系统的结论。这和你 taxonomy.md 里 `experiment_hazard` 标记是同一类问题，值得在那一节里加一条。

## 六、IF 类怎么自动判——统计离群法

IF 类没法靠注入判定（注入的时候你并不知道这个错误"本该"可恢复还是不可恢复）。WASABI 的做法是统计：对每个异常 E，数出代码库里能抛出 E 的重试循环总数 N_E，和其中真的重试了的 R_E，算全局重试比 R_E / N_E。**比值很接近 1 但不等于 1（或很接近 0 但不等于 0）的，就是离群点**。阈值取 ≥2/3 或 ≤1/3，报了 9 例，8 例确为真问题。例：`KeeperException` 在 20 个重试循环里被重试了 17 次。

这个"用代码库自身的多数行为当规范"的思路，可以迁移到你的规则库：**同一个集群里，同一个依赖被 N 个调用方引用，其中 N-1 个配了超时/重试，剩下那个没配**——这比"必须配超时"这种绝对规则误报低得多，而且能自动从被测系统里挖出来。

## 七、边界与注意

- 全是 Java 系统，重试靠异常驱动。Kafka 被排除在工具评估之外，就是因为它的重试主要由**错误码和应用状态**驱动而不是异常——你的被测系统如果是 Go/gRPC，错误码驱动是常态，WASABI 的注入手法不能直接照搬，但三个 oracle 可以。
- 误报率不低：单元测试路线 2 真 : 1 假，静态分析路线 1.4 真 : 1 假；GPT-4 报了 79 个 WHEN 缺陷但也带了 60 个误报，而且它在大文件上（平均 1 万行）经常认不出重试逻辑，漏了 100 个重试循环。**不要把"大模型识别机制位置"当成可靠输入**，它和传统静态分析是互补关系（CodeQL 认出了 85% 的重试循环但完全看不见非循环重试）。
