# 取消传播（OSDI 2022）

- 全称：*Cancellation in Systems: An Empirical Study of Task Cancellation Patterns and Failures*
- 作者：Sethi、Pan、Lu、Musuvathi、Nath
- 缓存：`manifestations-v1/docs-cache/STU-CANCEL-SETHI22.txt`

## 一、它做了什么

13 个系统（Java：Cassandra、Elasticsearch、Hadoop 全家、HBase、Hive、Kafka、Solr/Lucene、Spark；C#：ASP.NET Core、Roslyn；Go：CockroachDB、etcd、InfluxDB），**62 个"请增加取消能力"的需求**和 **156 个取消相关缺陷**。另外用 CodeQL 实现了 5 个反模式检查器，在这些系统的最新版里找出约 200 处。

## 二、最该搬走的：三阶段分解

取消被拆成三个阶段，缺陷按阶段归类。这个分解比"超时"这个词精确得多——**超时只是取消的触发器之一，超时返回了不等于下游停了**：

| 阶段 | 子类 | Java | C# | Go | 说的是什么 |
|---|---|---|---|---|---|
| **发起**（约 30%） | 漏掉触发器 | 22 | 3 | 9 | 该发起取消的事件没有对应逻辑 |
| | 触发器判断写错 | 7 | 0 | 0 | 知道要判，但判"某任务是否在跑"的逻辑不对 |
| | **误取消** | 7 | 1 | 0 | 取消了不该取消的任务 |
| **传播**（约 25%） | 送达不及时 | 15 | 3 | 4 | 竞争导致请求被丢；或目标卡在阻塞调用里长时间不查标志 |
| | 取消被吞掉 | 17 | 5 | 2 | Java 的 interrupt 被调用链上的方法悄悄清掉；C#/Go 的 token 没往下传 |
| **落实**（约 33%） | 没检查 | 8 | 0 | 4 | 长循环里从不查标志 |
| | 检查了不执行 | 6 | 0 | 0 | catch(InterruptedException) 块是空的 |
| | **清理有缺陷** | 23 | 5 | 6 | 停下来了但资源/共享状态没恢复 |

> **订正你 gaps.md 的一条判断**。你写的是"`cancellation b`（不该取消却取消）——Sethi 全文查过，论文的五类反模式全是'取消没做到'，没有'误取消'的类别"。五个**反模式**（§7）确实都是"没做到"，但**根因分类**里有 §5.1.3 **Excess cancel**，8 条：
> - 任务 T 启动时，误取消了实际上不冲突的任务（CASSANDRA-13142、CASSANDRA-15024）；
> - 确实冲突、但优先级比 T 更高的任务被取消了（HBASE-17674）；
> - 任务 T 完成时，取消了与 T 相关但结果仍被需要的任务（roslyn-11470、HADOOP-6762）。
>
> 这三种形态都是可写成条目的 b 类。`cancellation b` 这一格可以补上。

## 三、清理缺陷的结构化拆解（Table 5）

这张表比"清理不干净"这句话有用得多，可以直接变成你 `distinguishing_signals` 的枚举维度：

- **哪种缺陷**：清理动作本身写错 10 / 清理不完整 14 / 完全没清理 4 / 清理顺序错 3 / 其他 3
- **要清理的数据在哪**：堆内 27，持久化 7 —— **80% 是堆内数据**
- **怎么清理**：把数据置无效或回滚 13 / 释放资源（锁、线程、token）13 / 删文件 2 / 其他 6

两个具体案例值得记：
- SOLR-8372：恢复任务被取消后，update log 本应保持 `inactive` 直到恢复重启，清理逻辑却错误地置成了 `active`，**后果是可能丢数据**。
- CASSANDRA-7803：compaction 的结果文件可能写到正式位置或临时位置（取决于配置），清理只删了正式的，临时文件很快把磁盘填满、应用不可用。
- CASSANDRA-15674：任务对共享的 `SystemMetrics.totalDiskSpaceUsed` 做了一次加法，取消时必须减掉同样的值——**这说明有些清理要求任务自己记住做过什么修改**，不是无状态的。

## 四、症状分布（Table 6）

156 条里能确定症状的：资源泄漏 30、性能问题 29、任务 API 被打坏 17、数据损坏或丢失 5、**向用户报错状态 10**、未说明 65。

"向用户报错状态"这一类值得单独注意：**系统报告任务已取消但其实没取消**（HIVE-14942、SPARK-18665、influxdb-13681），或反过来**报告没取消但其实已经取消了**（SPARK-2666）。这是"系统自述状态与实际状态不一致"，和 Gray Failure 的 differential observability 是同一件事的另一个侧面——只不过这里的观察差异发生在**系统与用户之间**，而不是系统内部观察者与应用之间。你的目录里 g 类（错误数据）目前只讲返回内容，可以把"状态自述不符"也纳进 g 的判据说明。

## 五、机制本身成为瓶颈

两条反直觉的：

- **elasticsearch-75316**：取消的使用频率被低估，取消处理的实现效率太低，导致**正常用户请求延迟涨了 50 倍**。补丁是让取消处理更高效。取消机制本来是为了省资源，结果成了瓶颈。
- **HIVE-13858**：interrupt 信号被吞掉 → 任务陷入无限循环 → 该部分系统 I/O 完全不可用 → 可能导致**整个集群不可用**。CASSANDRA-11373 同理：清理不完整 → 无限循环 + CPU 打满。

这两条是 c 类（无界）和 d 类（放大）在 cancellation 组的实证，你目前 cancellation 组的 c 类只有一条。

## 六、语言机制决定缺陷形态（这一点对多语言 benchmark 很关键）

| 语言 | 机制 | 独有的坑 |
|---|---|---|
| Java | `Thread.interrupt()`，**每线程一个标志** | 标志会被调用链上的库方法**静默清除**（`sleep`、`poll` 等抛 `InterruptedException` 时会清标志）。`t.interrupted()` 查完就清、`t.isInterrupted()` 查而不清——用错就丢信号。因为机制太弱，Java 程序里大量自建 boolean 标志，于是又引入"目标卡在 `BlockingQueue.take()` 里长时间不查标志"的问题（SPARK-1582） |
| C# | `CancellationToken`，可以有任意多个 | 令牌靠函数参数传递，**漏传给某个长跑函数**取消就会被大幅延迟。一个函数通常只接受一个 token 参数，开发者得自己知道当前上下文有哪些 token、怎么合并 |
| Go | `Context`，同上 | 同 C#；另外 Context 里混了取消信号和其他信息，工具分析更难 |

C#/Go 一旦取消就**不可撤销**，所以没有 Java 那种"被清除"的问题。

对你的意义：**"取消是否传播"这条判据在不同语言栈上的可观测信号完全不同**。Java 栈要看 interrupt 标志有没有被某层吞掉；Go 栈要看 context 有没有断在某一跳。你的被测系统如果是 Go（gRPC + context），主要盯"invisible token"——某个长跑函数没拿到 ctx。

## 七、几个能防住这类缺陷的代码构造（值得写进 rules-v1 的"良好实践"）

论文收集的系统自建构造：

- **可取消任务接口**：Cassandra 的 `Interruptible` 接口强制实现 `interrupt()`；Elasticsearch 的 `CancellableTask` 抽象类预置了不可覆盖的 cancel 方法和 `isCanceled()` 查询方法。好处是**取消能力在类型签名上就是显式的**。代价：完全绕开内置 interrupt 后，任务卡在 `sleep` 这类阻塞方法里就出不来了。
- **取消后钩子**：Cassandra 的 `LifecycleTransaction` 提供 `onAbort()`，把散落的清理逻辑收拢到一处。
- **不可中断区段**：Spark 的 `UninterruptibleThread` 允许声明一段"必须整体执行完"的代码，`interrupt()` 会被压到区段结束后再生效。**专门用来保护清理逻辑本身不被二次中断打断**——论文里好几个"清理不完整"就是清理过程中又被 interrupt 打断造成的。但若区段里有无限阻塞，线程就永远不响应取消了。
- **任务依赖追踪**：Elasticsearch 的 `TaskManager` 要求所有任务带 `id` 和 `parentId`、都经由 manager 启动，取消也走 `cancelTaskAndDescendants`。这是对"漏掉触发器"里最常见的一种（父任务取消了、子任务没取消）的结构性防御。

## 八、边界

- 只看了 Java/C#/Go 三种语言的内置机制，不覆盖 C++、Rust 等。
- 作者自己说取消缺陷**报告不足**：取消代码在测试里很难跑到；而且从需求单的讨论看，实现取消太复杂，有时干脆劝退了开发者——所以"没有取消能力"这件事本身不会以 bug 形式出现在数据里。
