# 灰色失效：观察差异（HotOS 2017）

- 全称：*Gray Failure: The Achilles' Heel of Cloud-Scale Systems*
- 作者：Huang、Guo、Zhou、Lorch、Dang、Chintalapati、Yao（微软研究院 + Azure）
- 缓存：`manifestations-v1/docs-cache/STU-GRAYFAIL-HOTOS17.txt`

## 一、核心定义（你目录里已经用了，这里补全精确表述）

> **当至少一个 app 观察到 system 不健康、而 system 内部的 observer 观察到它健康时，这个 system 就处于灰色失效。**

模型里三个角色：**system**（提供服务）、**app**（使用服务，可以是另一个系统、用户或运维人员）、system 内部的 **observer**（主动或被动收集系统是否失效的信息）和 **reactor**（据观察采取恢复动作）。observer 和 reactor 都算作 system 的一部分。

2×2 的可能性表（Table 1）值得完整搬进你的 taxonomy：

| | app 观察良好 | app 观察异常 |
|---|---|---|
| **observer 观察良好** | ① 无失效 | ② **灰色失效**：用户在受苦，reactor 不会被调用 |
| **observer 观察异常** | ③ 好的那种观察差异：app 还没受影响，observer 已知有问题并会主动修复（若是误报则是另一类问题） | ④ 崩溃/fail-stop：双方一致，问题很快会被纠正 |

**时间演化**（§3.3）：系统先经历被它自己压制住的轻微故障（**潜伏失效**）→ 逐渐进入外部可见但 observer 看不见的退化模式（**灰色失效**）→ 退化到把系统打垮（**完全失效**），此时 observer 也看见了。即 ① → ② → ④。间歇性的灰色失效会**反复**走这个过程。

> 这条对你的实验窗口设计有直接影响：**如果注入强度足够大、观察窗口足够长，所有灰色失效最终都会变成完全失效**，而那时它就不再可区分了。你的 `upper_bound_note` 字段管的正是这件事——但灰色失效还多一个**时间上界**：观察太久，②就退化成④。所以灰色失效类条目需要同时写强度上界和**时间上界**。

## 二、三个可以直接写成条目的反常案例

### 1. 冗余越高反而可用性越低（§2.1）

Clos 网络里核心交换机崩溃时路由协议会绕开，但**随机静默丢包时不会重路由**。对于扇出型工作负载，论文给了一个可计算的公式：

> 若有 n 台核心交换机、扇出因子为 m，则某台核心交换机被一次请求经过的概率是 **1 − ((n−1)/n)^m**，随 m 增大**迅速逼近 100%**。

于是每个前端请求几乎必然经过每一台核心交换机，**任何一台的灰色失效都会拖慢几乎所有请求**。核心交换机越多，其中至少一台处于灰色失效的概率越大——**增加冗余反而伤害可用性**。

这是一个**罕见的、可写成公式的强度下限**。你目录里 `intensity_lower_bound` 要求"用机制参数写成公式"，这条正好符合：给定扇出 m 和冗余度 n，注入一台后端的随机丢包，受影响请求比例是 1 − ((n−1)/n)^m。

### 2. 恢复动作杀死系统而非治愈（§2.3）

Azure Storage：某数据服务器严重容量吃紧，但一个资源上报的缺陷让存储管理器没能检测到 → 管理器继续往它路由写请求 → 它崩溃重启 → 重启没有解决根因 → 管理器又往它路由 → 再崩溃。**反复若干次后，故障检测器发现它在反复重启，判定它不可修复，将其移出服务** → 可用存储总量下降（外加复制流程里的另一个微妙问题）→ 剩余健康服务器压力增大 → 更多服务器退化并走上同样的路 → 最终级联崩溃。

这一条把 a 类（该动不动：容量压力没被检测到）、b 类（不该动乱动：重启健康但过载的节点）、d 类（放大）、e 类（不恢复）串成了一条完整的链，是你 `interaction` 组的理想素材。而且它示范了一个重要机理：**灰色失效被误判成 fail-stop 之后，针对 fail-stop 设计的恢复动作（重启）会把情况变得更糟**。

### 3. 互相甩锅（§2.4）

VM 跑在计算集群、虚拟磁盘在存储集群、经网络访问。存储或网络出问题导致 VM 访问不了虚拟磁盘、VM 崩溃；**如果没有故障检测器发现存储或网络的底层问题，计算集群的检测器就会把失效错误地归因到 VM 里的计算栈**。论文说他们确实遇到过不同子系统的团队互相指责、因为谁都拿不出真正原因的证据。

> 这条对你的 evaluator 是个直接的警示：**故障归因的正确性本身应该是一个被评测的能力**，不只是"有没有恢复"。一个把网络问题归因成应用问题的智能体，即使最后碰巧恢复了服务，它的诊断也是错的。

## 三、解法方向（可作为规则库的"良好实践"）

- **§4.1 关闭观察差距**：从"单一的故障检测"（心跳）转向**多维健康监控**。论文的类比很好用：判断人体状况不能只看心跳，还要看体温、血压。
- **§4.2 近似应用视角**：让系统测量一些**近似于其 app 所观察到的**指标。例如用 Pingmesh 那样的服务器到服务器延迟与可达性探测来模拟常见应用对网络的观察。**警告**：过度主动的探测会给本已退化的系统增加负担，进一步伤害健康。
- **§4.3 利用规模**：灰色失效常常源于单个观察者的孤立观察，**聚合大量互补组件的观察**能快速揭示它。聚合点的位置是个设计权衡：太靠近系统核心，能观察到的东西有限；太靠近应用，系统内建的容错机制会把故障掩盖太久才暴露。

## 四、与其他篇的连接

- 和 **Metastable**：fail-slow / 灰色失效可以**作为触发器**引发亚稳态失效。
- 和 **Operator (NSDI'26)**：Gu 那篇直接引用了这一篇，说 operator 的探针"无法应对慢失效、灰色失效、部分失效和亚稳态"。
- 和 **Avizienis**：灰色失效在 2004 年的词汇里是"**unsignaled failure**"（检测机制没有发信号）。Avizienis 早就把检测机制自身的两种失效模式写清楚了：**误报（false alarm）和未发信号的失效（unsignaled failure）**。Gray Failure 的贡献是把后者放到云规模下重新论证，并给出 differential observability 这个更操作化的定义。
