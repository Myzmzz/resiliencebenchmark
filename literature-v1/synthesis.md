读完 12 篇之后，把结论按"能不能直接用"分成五块：**一个更准的分类骨架**、**一个顶层叙述**、**实验方法**、**判据设计**、**可量化的关系**。每条都标了出处。

## 一、分类骨架：两轴不够，是三轴

你现在的目录是两轴：**机制类别**（timeout / retry / circuitbreaker / …，11 组）× **缺陷形态**（a–g，7 类）。这两轴是对的，但读完之后能看到一件事：

> **四篇独立研究不同机制的论文，各自都把机制拆成了三个阶段，而且拆法几乎一样。**

| 出处 | 研究对象 | 阶段 1 | 阶段 2 | 阶段 3 |
|---|---|---|---|---|
| WASABI（SOSP'24） | 重试 | **IF** 该不该重试 | **WHEN** 何时、几次 | **HOW** 怎么重试、状态怎么收拾 |
| Sethi（OSDI'22） | 取消 | **发起** 谁该被取消 | **传播** 信号到没到 | **落实** 停下来、清干净 |
| Larsson（arXiv'21） | 熔断 | **传感器** 看什么指标 | **决策** 何时算过载 | **执行器** 触发后做什么 |
| Avižienis（TDSC'04） | 容错通论 | **错误检测** | （信号是否发出） | **错误处理 + 故障处理** |

这不是巧合。它说明**机制内部有一个通用的生命周期**，而"该动不动"可以出在三个完全不同的位置：

- **阶段 1 坏**：信号没到传感器 → 这是 Gray Failure 说的 differential observability，也是 Avižienis 的 unsignaled failure；
- **阶段 2 坏**：信号到了但判定没翻转 → 阈值算错、窗口不对、样本不足、计数器被加了两次（YARN-8362 让实际上限变成配置值的一半）；
- **阶段 3 坏**：判定翻转了但执行没做对 → 熔断打开了流量还在走、取消发出了下游没停、重试重来了脏状态没清。

### 建议：加一个正交字段 `defect_stage`

值域 `sense` / `decide` / `act`，和 `class: a–g` 正交，和 `mechanism_group` 正交。三条理由：

1. **它让 a/b 的判据能写死。** 你的 taxonomy.md 现在说"判 a 要证明触发条件已满足"，加上阶段之后可以说得更具体：判 a 在 `sense` 阶段，要证明**信号本身没有到达机制**（探针探的那条路径根本不经过故障点）；在 `decide` 阶段，要证明**信号到了但阈值没被跨过**；在 `act` 阶段，要证明**判定已经翻转但行为没变**。这三种在实验里要采不同的证据。
2. **它解释了为什么修复方式完全不同。** 同样是"存活探针没摘掉坏实例"，`sense` 坏要换探测路径（AWS Builders' Library 说的深度健康检查），`decide` 坏要调 `failureThreshold`，`act` 坏是 kubelet 或 Service 的问题。你的 benchmark 要评测智能体的诊断能力，这个区分就是评分点。
3. **它的成本很低。** 56 条里绝大多数已经隐含地写清了发生在哪一阶段，补字段是标注工作而不是重新抽取。

### 另一个建议：机制组缺一类——**执行恢复动作的控制器**

你现在的 11 组全是"应用侧或平台侧的防护动作"。但在 K8s 环境里，副本数、滚动更新、故障转移、扩缩容这些**恢复动作的执行者是控制器（operator）**，而 Gu 等（NSDI'26）的 412 起失效表明：

- **52.2%** 的 operator 失效来自交互缺陷，是内部程序缺陷（25.2%）的两倍；
- 交互失效里 **62.3% 后果是灾难性的**（全站不可用 50.2%、部分不可用 8.8%、静默丢数据 3.3%）；
- 最大的一类是**与被管应用的交互**（42%），而现有的测试与验证工具全都是应用无关的，完全不覆盖这一块。

控制器的缺陷形态和现有机制组对不上：**违反应用的操作语义**（63.7%，细分为配置 36.2% / 顺序 31.0% / 前置条件 19.0% / 执行环境 13.8%）、**看不见应用内部状态**（16.5%）、**版本不兼容**（12.1%）、**误处理应用错误**（7.7%）。这些既不是超时也不是熔断，归不进任何一组。

建议新增 `reconcile`（调谐与管理操作）组，或者至少在 gaps.md 里记一笔"这是本轮范围之外但确实存在的机制类别"。

## 二、顶层叙述：你测的是机制的 coverage

Avižienis 等（TDSC'04）给了一个 2004 年就定型的词，正好命名你在做的事：

> **任何给定容错技术的有效性度量称为它的 coverage**，定义为**在错误或故障已经发生的条件下，该技术有效的条件概率**。

而 coverage 的缺失分三层，**这三层可以直接当你 benchmark 报告的顶层结构**：

| 层 | 含义 | 对应你目录里的 | 典型论文 |
|---|---|---|---|
| **机制自身有实现缺陷** | 容错机制相对于它自己声明的故障假设就是错的 | a/b/c 类的大部分 | WASABI、Sethi、Yuan |
| **failure mode coverage 缺失** | 失效的组件**没有按假设的方式行为** | a 类里的"观察盲区" | **Gray Failure 整篇**（假设 fail-stop，实际 fail-slow） |
| **failure independence coverage 缺失** | 假设失效独立，实际是共因 / 反馈 | d、e 类 | **Metastable**（45% 事故多触发器）、Gray Failure 的"高冗余反而伤害可用性" |

同一篇还给了"可信性基准测试"的定义：**"一种在故障存在的情况下评估计算机系统行为度量的流程"**，用途是刻画系统的可信性，以及按属性比较可替代方案。这句话可以直接放进你的引言。

还有一句值得单独记，它几乎就是你整个研究方向的一句话依据：

> **容错是递归的：实现容错的机制本身必须被保护，以免受到可能影响它们的故障。**

## 三、实验方法：七条可以直接改进你 harness 的做法

### 1. 强度是二维的，单点实验对 e 类无效

Metastable（OSDI'22）的 MongoDB 实验：6200 rps、3 秒超时最多重试 4 次，注入"限制主节点 CPU"：

- CPU −78%、持续 10 秒 → **恢复**
- CPU −**80%**、持续 10 秒 → **亚稳态失效**，goodput 降 90%，永不恢复
- CPU −80%、持续 **9 秒** → **恢复**
- CPU −80%、持续 10 秒，但基线负载降 30% → **恢复**

**2% 的强度差、1 秒的时长差，分开了完全恢复和永久失效。**

所以：**e 类条目的实验必须扫 `(强度 × 时长)` 平面，产出稳定区 / 脆弱区 / 亚稳态区的分区图**，而不是一个是非结论。你的 `intensity_lower_bound` 目前只有强度一维，建议补 `duration_lower_bound`，或者把这个字段的语义改成一个二元组。

### 2. 同一个注入点要跑两种注入次数

WASABI 的做法：每个注入点跑两轮，K=1 和 K=100（或 1000）。

- **K=1** → 让重试之后的代码真的执行 → 暴露 HOW 类（状态没清干净）。论文的 HDFS 例子：注一次 `SocketException`，测试挂在空指针上，因为错误来得太早对象还没构造完，而 catch 块假设对象都在、打日志时就炸了。
- **K=100+** → 撑满上限和退避 → 暴露 WHEN 类。但这时重试之后的应用代码可能根本不执行。

一轮兼顾不了。这是**和强度正交的第三个实验维度：注入的重复次数**。

### 3. "持久故障 → 撤除 → 检查最终收敛"的 e 类协议

OAT（NSDI'26）测容错的做法，比单纯"撤除后观察"更强：

1. 先给应用注入一个**持久**故障；
2. 再声明一个**新的期望状态**，触发调谐；
3. 持久故障保证调谐**无法完成**；
4. **撤除故障**；
5. 检查应用状态**最终**是否匹配那个新的期望状态。

好处是它保证了故障期间确实有未完成的工作，而不是恰好什么都没在做。你的 e 类条目要求有明确的"撤除时刻"，这个协议给了撤除时刻之前该做什么。

### 4. 实验装置本身会掩盖机制

WASABI 发现：**约 10% 覆盖重试逻辑的单元测试里，开发者手动把重试上限改成了 0、1 或 2**，所以他们写脚本扫描并改回配置文件里的默认值。

对你的直接警示：**被测应用在 demo / 测试环境下的机制参数，可能和生产不是一回事**。如果 harness 沿用示例的 values 文件部署，测出来的"有没有重试"可能是装置的结论。这和你的 `experiment_hazard` 是同一类问题，建议在 taxonomy.md 的那一节加一条。

### 5. 复现的规模边界（Yuan, OSDI'14，198 起生产故障）

- **98% 的故障在不超过 3 个节点上就能显现**，84% 不超过 2 个 → 你的三节点环境在这个意义上够用；
- **77% 需要多于一个输入事件，但 90% 不超过 3 个** → 单一扰动覆盖不了大半，组合深度 3 够；
- **在需要多事件的故障里，88% 顺序重要** → episode 必须显式声明顺序，"同时注入 A 和 B"和"先 A 后 B"是两个实验；
- **74% 是确定性的** → 大部分条目应该能写成可重复实验；
- **38% 只在长跑系统里出现** → 需要显式的长跑 episode，短窗口看不到。

论文特意补充：这**不等于**"大集群不更容易出问题"，而是说**一旦给定那个特定事件序列，小集群就足以复现**。

### 6. 自下而上，而不是自上而下

Yuan 的建议，直接冲着随机注入去：现有做法是自上而下（启动系统、在各阶段主动注错），但残留的生产故障需要**罕见的事件序列先把系统带到罕见状态**，输入空间不可控。建议改成**从已有的保护/错误处理代码出发，反推能到达它的测试用例**。

**这条对 ORCAS 那条路线（架构感知地选实验）既是补充也是警告**：即使按机制和反模式选实验，仍然会漏掉"需要先把系统带到特定状态"的缺陷。你的 episode 里"前置状态"和"注入什么"同等重要。

### 7. 恢复粒度阶梯要显式测

Microreboot（OSDI'04）的递归恢复策略——**先试最便宜的**：微重启组件 → 重启 Web 层 → 整个应用 → JVM → 操作系统，全试完还不好才叫人；**发现重复的失效模式时也叫人**（防无限重启循环）。实测时间：单组件 411–601 ms、整应用 1028 ms、JVM 7699 ms、OS 19083 ms，**跨四级差约 46 倍**。

更反直觉的一条：**微重启不做故障转移平均 78 个请求失败，先切流量再微重启反而是 162 个**——因为坏节点在恢复期间本来还能服务大部分请求，切走要么让它们失败要么白白压垮好节点。

所以你的 benchmark 可以直接测：**同一个故障，系统（或智能体）实际选了哪一级恢复动作？在更便宜的动作足够时是否用了更贵的？恢复动作的影响面是否超出了故障的影响面？**

## 四、判据设计：五条

### 1. 与业务无关的三个判据（WASABI，可照抄）

| 判据 | 怎么判 | 抓哪类 |
|---|---|---|
| **无上限** | 同一注入点被触发 100 次，或单测试跑超 15 分钟 | 重试/重启无界 |
| **无退避** | 两次连续注入之间，日志里有没有**从同一个协调方法的调用栈上**发出的 sleep（`Thread.sleep`/`Object.wait`/`TimeUnit.sleep`/`Timer.schedule` 等） | 无退避 |
| **异常不同** | 最终抛出的异常 ≠ 注入的异常 | 状态没清干净 |

第三条的妙处：它顺手消化了机制定位的误报——如果那里根本不是重试点，注入的异常会原样抛出，自动判为非缺陷。

### 2. 判据必须超出平台 API（OAT，NSDI'26）

**86 个新缺陷里 43%（37 个）必须靠应用特有的状态监视器和工作负载才能抓到**，用"检查崩溃、错误日志、K8s 状态对象"这类常规判据完全看不见：33 个表现为**应用真实配置状态与 ConfigMap 对象不一致**，4 个表现为**状态转换期间的瞬时不可用**。

两种工具，成本明确：

- **状态监视器**：以 MariaDB 为例——跑 `SHOW VARIABLES` 拿当前配置 → 解析成键值对 → 与声明的期望配置比较。论文说配置状态监视器"实现起来很容易，但对检测配置类语义违反非常有效"。
- **应用工作负载**：周期性读写，**在状态转换的整个过程中**持续测成功率。因为"操作完成后再检查状态"看不见过程中的可用性违反（比如滚动升级破坏多数派 quorum）。判据是：普通操作期间可用性不下降；注入瞬时故障时可用性不低于 **95%**。

每个 operator 写 **88–208 行 Python**，接一个新 operator 约 **8 人时**。

> 这给了你 gaps.md 3.1 节那个判断一个方法论依据。你写"f/g 类空缺应该在具体被测系统上通过业务断言实验产出"——Gu 这篇把它变成了可执行的：**判据分两层**，平台可见的状态对象一层，应用内部状态 + 过程中可用性一层。

### 3. 服务复苏 ≠ 数据正确（Microreboot）

论文明确区分：**resuscitation**（恢复到能继续为所有用户处理请求，**不一定修好了数据库损坏**）vs **recovery**（以 100% 正确的数据库运行）。而且指出**金融机构常常只追求前者，在营业日结束时用补偿事务修复不一致**。

**建议写进 taxonomy.md 的 e 类判据**：e 类的"恢复"指服务复苏；数据是否正确属于 f/g，两者必须分别判定，不能用前者代替后者。一个系统完全可能撤除故障后 30 秒 SLO 全绿（e 类过），同时账上留着一笔重复扣款（f 类不过）。

### 4. 用 action-weighted throughput 代替请求成功率（Microreboot）

- 会话从登录开始，到显式登出或放弃结束；
- 会话由若干**用户动作**组成；
- 每个动作是一串操作，以一个**提交点**结束，这个操作必须成功整个动作才算成功；
- **提交点失败时，该动作里所有操作被追溯标记为失败**。

理由：长短操作都成功用户才满意；操作多的动作成功意味着用户完成了更多工作。而且"提交点"天然把 f 类的判定挂了进来——**提交点前后的状态正是业务断言最该看的地方**。

### 5. 用"代码库自身的多数行为"当规范（WASABI 的 IF 类判据）

IF 类（该不该重试）没法靠注入判定，因为注入时你并不知道这个错误"本该"可恢复。WASABI 的做法是统计离群：对每个异常 E，数出能抛出 E 的重试循环总数 N_E 和真的重试了的 R_E，算 R_E / N_E；**很接近 1 但不等于 1（≥2/3），或很接近 0 但不等于 0（≤1/3），就报离群**。报 9 例，8 例为真。例：`KeeperException` 在 20 个重试循环里被重试了 17 次。

**迁移到你的规则库**：同一个集群里同一个依赖被 N 个调用方引用，其中 N−1 个配了超时/重试，剩下那个没配——**这比"必须配超时"这种绝对规则误报低得多，而且能自动从被测系统里挖出来**。你的 rules-v1 里"需求相对型"的规则已经降级为弱判定了，这个思路正好给它一个更强的形式：不是相对于需求，而是相对于**同一系统内的多数实践**。

## 五、可量化的关系：能写进 `intensity_lower_bound` 的公式和数字

| 关系 | 公式 / 数字 | 出处 |
|---|---|---|
| 亚稳态稳定区 | `C_stable = C_norm / (w*_L · w*_C)`；`L_norm < C_stable` 则永不发生亚稳态失效 | Metastable 定理 2 |
| 过载触发条件 | `m_trigL + m_trigC ≥ C_norm − L_norm`；不满足则永不发生 | Metastable 定理 1 |
| 脆弱度随触发时长 | `w_L(Δt)·w_C(Δt) < C_norm/L_norm` 则安全；w 随 Δt 单调增 | Metastable 定理 3 |
| 已进入失效状态 | `L_sys − C_sys ≥ α_L·m_trigL + α_C·m_trigC` | Metastable 定理 4 |
| 重试上限与稳定区 | 最多 2 次重试 → 放大不超过 3 倍；**不设上限 = 稳定区为空** | Metastable §3.6 |
| 扇出下的灰色失效覆盖面 | 扇出 m、冗余 n 时，某台后端被一次请求经过的概率 = **1 − ((n−1)/n)^m**，随 m 迅速逼近 1 | Gray Failure §2.1 |
| 聚合响应的新鲜度 | `TTL_聚合 = min(TTL_子请求 i)`；Hipster Shop 里一个客户端请求平均分叉成 **13** 个服务间请求 | Soft CB §II |
| 缓存失效的放大倍数 | 丢掉一个 99% 命中率的缓存 = **100 倍**工作量放大 | Metastable §6.5 |
| 超时与脆弱性 | 超时 1 秒 → 2 秒，每个 RPS 点的脆弱性都下降（需要更大触发才失效）；**更长超时降低脆弱性但发现失败更慢** | Metastable §5.3.2 |
| 过载保护的收敛速度 | 需求突增到容量 1.4 倍时：Breakwater **20 ms** 收敛无崩溃，DAGOR **500 ms**、SEDA **1.58 s** 才从拥塞崩溃恢复 | Breakwater 摘要 |
| 局部限流的饥饿条件 | 某 API 路径上有 >1 个过载微服务，且在其中之一还有别的 API 与它竞争。阿里 trace 23481 个微服务：**涉及过载微服务的 API 中 44.4% 潜在易饥饿**；Online Boutique 里任一 API 流量突增平均造成 **3.4** 个微服务过载 | TopFull §2 |
| 扩缩容的时间常数 | autoscaler 要**几秒到几分钟**才能供给资源，这期间 goodput 严重退化；TopFull + HPA 比单用 HPA 多服务 **3.91 倍**请求 | TopFull §1、§6 |
| 恢复粒度阶梯 | 单组件 411–601 ms / 整应用 1028 ms / JVM 7699 ms / OS 19083 ms | Microreboot 表 3 |
| 便宜恢复放松检测要求 | 用微重启时，监控器可以花多达 **53.5 秒**检测，用户感知可用性仍优于"瞬时检测 + JVM 重启" | Microreboot §6 |

## 六、对现有目录的两处订正

### 1. `cancellation b`（不该取消却取消）不是空缺，证据在

你的 gaps.md 写："Sethi OSDI 2022 全文……论文的五类反模式全是'取消没做到'，没有'误取消'的类别"。

五个**反模式**（§7）确实都是"没做到"，但**根因分类**（§5.1.3）里有 **Excess cancel**，8 条，三种形态：

- 任务 T 启动时，误取消了实际上不冲突的任务（CASSANDRA-13142、CASSANDRA-15024）；
- 确实冲突、但优先级比 T 更高的任务被取消了（HBASE-17674）；
- 任务 T 完成时，取消了与 T 相关但**结果仍被需要**的任务（roslyn-11470、HADOOP-6762）。

三种都能写成 b 类条目。

### 2. `retry b`（不该重试却重试）同样可补，WASABI §2.2.1 有四个具体案例

你的 gaps.md 说"这个格子最接近可补，缺的是一个具体案例"。WASABI 有四个，都带代码路径：

- **HADOOP-16580**：重试策略重试 `IOException`，但它的子类 `AccessControlException` 是权限失败，不该重试；
- **HADOOP-16683**：`setupConnection` 正确地不重试 `AccessControlException`，但别的路径把它包进 `HadoopException`，**后者总是被重试**——补丁要拆包才能区分；
- **ElasticSearch-53687**：`ResultsPersisterService` 把任务取消当成可恢复错误，**无限重试写结果**；
- **HIVE-23894**：任务处理器把被取消的 TezTask 当作失败**重新入队**，补丁是加 `isShutdown` 判断。

后两条同时也是 `cancellation` 与 `retry` 的交叉：**把"取消"误判为可恢复错误**，属于 `interaction`。
