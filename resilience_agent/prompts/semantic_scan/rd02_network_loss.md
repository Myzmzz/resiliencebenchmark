# RD-02 风险：网络丢包时重试和幂等保护不足；后果：请求被放大，写操作重复或数据不一致

本模板只使用ChaosBlade原子故障`network-loss`，对应`k8s pod-network loss`。不得把丢包本身写成缺陷；必须找到丢包会激活的重试放大或业务一致性弱点。

先从真实业务入口定位HTTP/gRPC/DB/MQ等远程操作，区分只读调用、幂等写入与非幂等副作用。用CodeGraph展开调用方、统一包装、SDK、拦截器和被调用方，核对每层attempt、timeout、backoff、jitter和共享预算。对写操作继续检查幂等键的生成/传播/存储、服务端去重、事务边界和对账补偿。

主动查找反证：单层有界重试、全局尝试上限、指数退避抖动、断路器、幂等存储、唯一约束、Outbox/Inbox或对账流程。仅“使用了重试”不是缺陷，仅“没搜到幂等”也不足以否定其存在。

候选机制必须能被有界部分丢包区分：预期观测为单个逻辑操作的尝试数放大、下游RPS超过入口RPS、或重复/丢失业务副作用。无法定位可注入方向、独立对账Oracle或可清理边界时，不得标记为可出题candidate。

边界必须严格：只有Deadline/取消错误时属于RD-01；Pod中断后的本地持久化或重放错误属于RD-10。单层有界重试且幂等边界完整时必须`not_found`。

`available_fault_types`只能包含`network-loss`。机制主要是重试放大时选D5；是副作用/一致性边界时在模板允许D类中依证据选择，不得仅凭缺陷名称分类。
