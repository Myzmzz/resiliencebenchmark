# WP-E：残留判定下沉到目标侧（2026-09-12）

方案把 WP-E 标为「最关键的新能力」，并且是 WP-F 的硬性前置闸门。
本文记录判据设计与集群实测结果。

---

## 一、为什么现有平台是瞎的

现在的「两层检查」其实**两层都在集群面**：私有台账 × 集群 CR 列表
（`fault_inventory.py:137` + `:99`），全仓没有任何进程级探测。

进程内 shim 时代这是成立的——我们自己发的命令自己记账。**黑盒后这个前提消失了。**
2026-09-11/12 那轮留下两个确凿反例：

- **D8-B**：撤掉正规注入权限、只留 `kubectl exec`，BladeAI 在目标容器里用
  shell 死循环手搓了 CPU 燃烧器。独立观测 CPU **3m → 811m，约 300 秒**，
  **集群里一条故障记录都没有**。
- **F5**：即使走正规路径，删掉集群记录也不停止机器上的进程——cart 删完记录仍在
  **1023m**，必须进工具容器 `blade destroy` 才真停。

## 二、判据（`stage2_service/target_residue.py`）

按权威性排序，每一条都有出处：

| 顺序 | 判据 | 为什么是这个顺序 |
|---|---|---|
| 1 | **探测失败 = `unverified`** | 看不了 ≠ 看过了没有。沿用 `fault_inventory` 既有原则：「失败的 CRD 列举不能变成干净的环境」 |
| 2 | **指标未回落 = `residual`**，无论集群面怎么说 | 这就是 D8-B：集群里零记录，CPU 在 811m |
| 3 | 必需指标没采到 = `unverified` | 沉默不能读成干净 |
| 4 | 进程 / tc 规则是**佐证** | 能证明有残留，但不能单独证明没有 |

**容差**：`max(基线 × 2.0, 基线 + 下限)`，CPU 下限 50m、延迟 20ms。
两者都要的理由：cart 空载 3–4m，纯比例会把正常抖动判成残留；纯绝对值又会在
繁忙负载上漏判。实测故障态 780–1023m 与 79ms，与容差差一个数量级以上，区分很干净。

**`residue_clear` 是新的权威判据** = 集群面干净 **且** 目标侧干净。
`inventory_clear` 语义保持不变（集群面），因为现有十几处消费方都按那个语义读。
未配置巡检时两者相等，所以其他三家现状不受影响；配置了但探测失败则
`residue_clear` 为假，而不是静默变干净。

## 三、集群实测（2026-09-12，旧环境）

**不新建任何部署件**，复用已常驻的组件。四条路径逐一验证：

| 路径 | 结果 | 用途 |
|---|---|---|
| `kubectl top pod` | cart = **4m** | 首要判据 |
| 容器内读 `/sys/fs/cgroup/cpu.stat` | `usage_usec` 可读；`nproc=8`、`cpu.max=max 100000`（无配额） | 精简镜像 / 无 metrics-server 时的备选；BladeAI 自己在 D8-B 就是这么测的 |
| 经 `chaosblade-tool` DaemonSet 查节点侧 | 每节点一个 Pod、**已跑 33 天**；当前无注入进程、无 netem 规则 | 机器级证据，无需新部署 |
| `blade status` 账本 | 可读，但**证明了自己不可信**（见下） | 仅作线索 |

目标 `cart-7c58f6bb56-jzz9b` 在 `tcse-v100-02`，对应工具 Pod `chaosblade-tool-smlw5`。

### 账本不可信——F9 当场复现

账本里实验 `2ec1be57adba4e96`（network delay，2026-09-11 11:48 创建）
到 2026-09-13 仍标着 **`Status: "Success"`**，而同一时刻实测：
**目标上一条 tc 规则都没有**，延迟正常。

而且这不是孤例：账本里积了 **90+ 条**这样的记录，最早回溯到 2026-03-25，
大量 `Status: Success` 的幽灵。**平台若信账本，会凭空判出一堆不存在的残留。**
这直接坐实方案里「账本只能当线索，结论以实测为准」那条。

### 累积量不能直接当速率

cgroup 的 `usage_usec` 是**累积值**，故障停了也不会回落——直接拿它判恢复
等于判不出来（坑 6 记的正是这个）。因此由两次读数与间隔算速率：
实测换算逻辑在 `millicores_between()`，1 秒内烧掉 0.8 CPU-秒 = 800 毫核，
正是 D8-B 燃烧器的真实强度。

## 四、验收

方案要求的回归用例（D8-B：集群里没有故障记录、但目标 CPU 未回基线）
已固化为 `tests/test_target_residue.py::test_a_burner_with_no_cluster_record_is_caught`
与 `::test_the_cluster_face_alone_would_have_called_that_clean`——
后者明确断言 `inventory_clear is True`（集群面一尘不染）而
`residue_clear is False`（权威判据仍判不干净）。

22 项测试全绿，用的数字都是实测值（3m 基线、811m / 1023m 故障态、79ms 延迟）。

## 五、尚未接线

判据与解析器已就位，**运行时采集尚未接入** `snapshot_for_trial` 的调用点
（`runtime_factory.py:1272`、`fault_inventory.py:179`）——那需要平台侧的 kubectl
执行通道，属于正式接线。接线前 `residue_clear` 恒等于 `inventory_clear`，
行为与现状一致。

**WP-F 的前置条件**：本包验收通过，但「验收」应包含一次带真实注入的端到端核验
（注入 → 指标升高被测到 → 恢复 → 指标回落被测到）。本次未做真实注入，
故 WP-F 的删除动作仍**不应**开始。
