## 第一次为什么是 CASE_INVALID

五项实验闸里只有一项没过：

```
target_verified: true        main_fault_running: true      fault_absent: true
chaos_inventory_clear: true  business_recovery_verified: false   ← 唯一一项
```

`reason_codes=["HARNESS_TIMEOUT"]`。`scripts/run_harness_trial.py:60` 写死
`DEFAULT_TIMEOUT_SECONDS = 30*60`，`NativeHarnessRunner` 构造时没传这个参数，
也没有环境变量能改——**30 分钟是硬预算**。

智能体做完了全套（选目标、建基线、注入、验效果、要求清理、清理成功、
故障确实消失、故障清单归零），但在提交结构化结果之前被掐断，所以
`business_recovery_verified` 拿不到平台侧的确认。恢复记录里能看见这个断点：

```
agent_observed_business_recovery: true     ← 智能体自己观察到了
business_verified_by: null                 ← 但平台没拿到可归因的确认
```

同时留下一条 INFO 级 `OUTPUT_UNSTRUCTURED`。

### 时间花在哪：96% 是模型推理

从 `gateway-usage.jsonl` 算的，不是猜的：

```
24 次网关调用，0 次重试
模型总耗时 1453s / 墙钟约 1510s  →  96%
调用之间的间隔（智能体自己干活+工具往返）只有 4–7s
最慢的五次： 190s, 178s, 161s, 151s, 116s
峰值输入     272,693 tokens
```

**不是环境慢**：同期单独测网关，`qwen3.8-max` 小上下文一次 2.4–6.6s。
是上下文涨到 27 万 token 之后，单次推理要 2–3 分钟，24 次就把 30 分钟吃光了。

也**不是 DNS 兜底拖的**——调用间隔一共才 4–7s，而 DNS 每条连接最多 2–4s
且连接是复用的。（DNS 那件事见
[P7 的记录](stage2-env3-p7-options-20260912.md)。）

另外 `stderr.txt` 里有一条，发生在最后一次调用（03:37:03）：

```
ERROR codex_core::mcp_tool_call: failed to parse tool call arguments: expected value at line 2 column 1
```

模型吐了不合法的工具调用 JSON。只有一条，不是主因，但记下来。

## 第二次做了什么改动

**只换了模型**，`qwen3.8-max` → `deepseek-v4-flash-0731`。提示词、用例、
交互模式、平台配置一个字没动。

没有去调那个 30 分钟的预算。那是平台常量，**为了让自己的验收通过去改平台代码
是不能干的事**，也不在本批整改的 6 条范围内。

中途还撞到两件事，都是平台该有的行为：

- 第一次提交被拒：`gateway_probe_in_progress`——探测没跑完不让提交，
  这是对的 fail-closed，等探测 complete 再提交即可。
- `qwen3.8-flash` 这一轮探测变成了 `probed_with_unsupported_capabilities`，
  于是从可跑集合里掉了出去（上一轮它还是 `supported`）。能力探测在这个模型上
  **不稳定**，值得留意；平台的处理是对的——不可跑就不给用。
